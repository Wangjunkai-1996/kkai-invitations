# 销售邀请与人工结算

销售账号继续使用 NewAPI 的登录、用户 ID 和邀请码。管理员在「邀请管理 → 销售账号」中登记现有用户 ID；不增加 NewAPI 管理员权限、不更改计费分组。停用后保留客户和历史返利的查看权限，停止新的申请。不能通过停用销售身份把销售申请转成普通余额返利。

## 用户与管理员操作

1. 管理员登记销售账号，填写内部备注。
2. 销售登录后分享原邀请码/邀请链接，在「受邀客户」查看总邀请、有效邀请、邀请日期、首次充值、充值明细及返利状态。
3. 新订单返利从支付完成时刻起冷却七天。到期后销售选取可申请记录，提交人工审批；原有最低申请金额、申请频率和返利来源开关仍生效。
4. 管理员在独立「销售审批」队列批准或拒绝。普通申请和销售申请按**提交时的身份**分类，后续身份变更不改历史类别。销售申请永不自动批准。
5. 管理员自行在外部处理付款，再填写凭据或说明，点击「确认已发放」。这一步只登记事实，不向任何账户转账。不支持部分确认；重复确认不会产生第二笔发放记录。

销售申请不依赖普通「转入余额」开关。销售申请禁止走单笔、批量审批并发放及逐条余额发放接口。资金维护模式仍可阻止财务确认。

## 统计与金额口径

- 总邀请人数：NewAPI `users.inviter_id` 指向本人的历史客户数量，含软删除客户。
- 有效邀请人数：客户存在至少一次正额成功的钱包充值，按人去重。余额后来用完不失效。赠送余额、兑换码、站内余额付款和订阅充值镜像不计入。
- 人头奖励不计算、不生成；仅提供人数。
- 累计到账充值额度：从 NewAPI 成功充值事件的不可变 `credited_quota` 取值；按已核定的币制边界转换旧额度。不是原支付金额，也不代表实收人民币。
- 历史订单缺少可核实的到账快照时，仍计入充值与有效邀请，金额显示待核对，并返回未知金额订单数；不按当前费率猜测、不将跨渠道的 `money` 字段直接相加。
- 返利按 Invitations 原始账本汇总，分别显示冷却中、可申请、待审批、已批准待处理、已确认发放；锁定、关闭、待计算额外说明。无返利记录的充值显示尚未生成，不冒充零返利。
- 客户看板只汇总来自客户的返利，排除销售本人作为被邀请者得到的注册奖励。自己的注册奖励仍在原返利记录/申请中保留。
- 金额在服务端以整数额度/精确数值聚合后转换为显示分值，前端不加总当前页。每个总计和明细各自显示舍入，亚分值可能产生显示舍入差；实际申请和发放凭据保存额度原值。
- 两个数据库之间存在事件同步延迟。客户/充值读取同一只读快照；返利是随后读取的账本状态，不承诺跨库原子快照。

现有订单费率与注册奖励规则沿用；没有新增销售专属比例、分级佣金、自动退款冲正或自动付款。异常订单仍需管理员按原有流程核对。

## API

接口实际前缀沿用部署的 `BASE_PATH`，前端通常经 `/invitations` 代理。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/invitations/sales-profile` | 本人的 active/registered 能力 |
| `GET /api/invitations/sales-customers?page=1&pageSize=20` | 自己的客户分页与全局统计 |
| `GET /api/invitations/sales-customers/{userId}/recharges` | 自己客户的充值分页 |
| `GET /api/admin/sales-accounts` | 销售账号分页 |
| `PUT /api/admin/sales-accounts/{userId}` | 登记/启停销售身份 `{active,note}` |
| `GET /api/admin/rebate-requests?requestKind=sales` | 销售审批；省略类别默认 ordinary |
| `POST /api/admin/rebate-requests/{id}/confirm-issued` | 全额人工确认 `{note}` |

审批、拒绝和重置复用原接口。申请响应新增 `requestKind`、`issuedAt`、`issueNote` 和币制信息。外部确认仍保留基础 `approved` 状态，由凭据派生已发放；不能将其当作站内余额付款的 `completed`。

## 迁移与交付

应用仓库：`new-api-kkai`（default 前端）。服务仓库：`kkai-invitations`（本仓库）。需要两者配套交付；源码完成不代表已部署。

Invitations 新增迁移 `202610140001_sales_accounts_and_settlement.sql`，包括销售身份与变更记录、申请类别、不可变人工发放凭据及保护约束。NewAPI 用户表与角色表不变。

迁移将首次安装时间持久化为 `order_rebate_seven_day_cutover_at`。订单完成时间达到该边界才使用新七天规则；更早但迟到的事件仍采用此前二十四小时规则。已落账记录的到期时间不重写；重放校验同时接受历史两天初始化/七天冷却、五分钟初始化/二十四小时冷却、新五分钟初始化/七天冷却。注册奖励原有即时生效及付费解锁规则不变；「每七天申请一次」与订单冷却是不同配置。

未来升级时先暂停旧 Invitations 入站/同步消费者，再执行受维护锁保护的迁移并启动新服务，避免旧实例在新边界后仍写二十四小时记录。NewAPI 的充值事件可继续保留在 outbox 待消费。本次开发不执行生产迁移、镜像构建或发布。上线须另按两个服务的正式发布与备份规程操作，不通过手改业务状态完成升级。

数据库迁移完成后不能仅回滚到不识别销售类别的旧服务；应保留新约束并使用理解该 schema 的版本处理。不得清空人工确认凭据来绕过检查。

外部确认保存当时币制和每条返利原始额度。已有的离线币制迁移可以转换当前账本投影，不能重写发放凭据。新增 USD 发放事实后，不再允许把投影恢复到旧币制；必须按实际财务历史处理，不能用币制恢复撤销已发生的发放。
